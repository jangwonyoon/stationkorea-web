## 실제 측정한 성능

같은 Chromium 156.0.8078.4·공유 Apple M4 Pro에서 모바일 390×844/라이트, 새 context·캐시 끔, CPU 4배 감속, 지연 150ms, 다운로드 1.6Mbps/업로드 750Kbps로 경로마다 3회 측정한 중앙값이다. 초기 load+5초 뒤 LCP를 수집하고 12단계 스크롤 후 CLS/전송량/긴 작업을 수집했다. CLS는 최대 세션 창 값이다.

|경로|LCP 전→후(ms)|CLS 전→후|초기 전송 전→후(B)|스크롤 후 전송 전→후(B)|JS 전송 전→후(B)|
|---|---:|---:|---:|---:|---:|
|홈|3544 → 3656|0.001548 → 0.016806|1,655,195 → 1,935,697|2,168,650 → 2,143,352|435,495 → 432,996|
|전체 기사|3440 → 3748|0.001461 → 0.001508|1,825,507 → 2,076,475|2,483,585 → 2,619,289|435,495 → 436,214|
|사당|4268 → 4196|0.001461 → 0.001571|1,803,817 → 1,860,570|1,954,900 → 2,056,679|435,494 → 436,593|

**홈(+112ms)과 목록(+308ms)의 LCP가 느려졌다. 성능 개선이나 production Web Vitals 통과로 보고하지 않는다.** 기존 #69의 LCP 목표는 이번 결과로 완료되지 않으며, 결과와 재현 방법을 그 이슈에 연결한다. LCP 대상은 본문 문단이었다.

양쪽 총 18회 페이지 HTTP 200, 페이지/콘솔 오류·가로 넘침 없음. 초기 긴 작업은 매회 1개, 최대 101→85ms. 스크롤 중 긴 작업은 양쪽 0개였다. 사당 변경 후 3회차에서 외부 Script 요청 하나가 `net::ERR_BLOCKED_BY_ORB`로 실패했고 그 회차만 정상 `cloud.umami.is/script.js` 응답이 없었다. 해당 실패를 삭제하거나 정상 회차로 대체하지 않았다. JS 중앙값은 외부 스크립트를 정상 수신한 회차의 값이다. 실제 Umami 이벤트 수신 검증 #37은 별도다.

[performance.json](./performance.json)에 환경·조건·회차별 측정·중앙값·오류 기록을 보존했다. 리소스별 원시 네트워크 행은 파일 크기를 줄이기 위해 제외했다. 재현: 빌드된 worktree에서 `node scripts/measure-design-performance.mjs http://localhost:<port> /tmp/design-performance.json`. 출력은 리소스 행도 포함한다.

로컬 Python HTTP는 gzip/Brotli·CDN·TLS가 없고 Next.js prefetch와 외부 스크립트도 전송량에 포함한다. 공유 호스트의 CPU/네트워크 모사이며 실제 휴대폰·production·현장 데이터·INP 측정이 아니다. Next 빌드 추정 First Load JS는 홈 약112kB 유지, 목록 약106→112kB이며 실제 CDP 전송량과 서로 다른 지표다.

## #146 기사 상세 누락 보완

이 문서의 앞선 검증은 홈·목록·공통 브랜드 중심이었다. 승인된 기사 상세 시안의 전체 폭 역명판까지 완료했다고 판단한 것은 잘못이었다. 사용자 재확인 뒤 #119를 다시 열고 실제 하위 이슈 #146에서 모든 역 기사의 배치를 보완했다.

- 입력: 사용자가 지정한 `역 기사 사당 · 1280-html/Article-1280.dc.html`. 격리 Chromium에서 실제 1280/768/390 렌더를 확인했다. 1280 기준 1200×380 역명판, 380×196 중앙 판, 아래 본문/레일 동시 시작이 핵심이다. 원본의 390 가로 넘침은 그대로 이식하지 않았다.
- 공통 `StationSign`과 `ArticleLayout`을 `/station/` 3편·`/article/` 역 기사 8편 모두 사용한다. 신규 기사에 없는 숫자 표·사진·릴스를 만들지 않고 관련 기사만 보조 영역에 둔다. 역 정보 없는 일반 기사에는 역명판을 강제하지 않는다.
- 역명판 가로 라벨은 기존 sign.prev/next, 세로 라벨은 공식 환승 자료의 개별 방면이 정확히 두 개 확인되는 노선만 표시한다. 합쳐진 문자열을 쪼개 추측하지 않고 “방면”을 유지한다. 김포/홍대의 미확인 노선 방면은 생략하고 성수는 확인된 지선 문구만 표시한다. 원고·수치·출처·dateModified와 기존 URL은 그대로다.
- `node --experimental-strip-types scripts/check-station-sign.mjs`: 사당 실제 데이터, 빈/하나/복합/세 방향의 생략, 중복 제거, 11편 출처 데이터 일치, 성수·김포·홍대 예외를 검증한다.
- `node scripts/check-station-article-design.mjs http://localhost:3260 /tmp/evidence-station-article-design`: 11편×3폭×2테마, 전체 폭·중앙 판 잘림·H1 위치·넘침·이미지/브라우저 오류, 대표 기사 axe, JS 없이 역명판/본문/링크를 확인한다. 증거 경로는 선택 인자이며 PNG를 레포에 커밋하지 않는다.
- 별도 담당자가 33개 실제 화면을 비교하고 패널-방면 라벨 교차 0·가로 넘침 0을 확인했다. 관련 기사 화살표가 혼자 줄바꿈되는 문제를 수정했다. 독립 코드 리뷰에서 발견한 역 없는 일반 기사 검사 분기도 보완했다.
- 기본 노선색·하차 안내·첫 그룹만 열림·출처·읽기 시간·정적 HTML/SEO를 보존했다. 신규 기사 breadcrumb는 기준 노선/역명으로 통일하고 화면과 JSON-LD를 같은 배열에서 생성한다.
- 빌드 추정 First Load JS는 기존 역 기사 약113kB 유지, 신규 기사 약112→113kB이다. 공통 클라이언트 레일 동작 재사용에 따른 증가이며 실제 CDP 전송량과 다른 지표다. 새 패키지·이미지 자산은 없다.
- 새 파비콘·실제 스크린리더 음성·production 배포는 이 보완 범위에 포함하지 않았다. 원본의 모든 보드를 대조했다는 의미가 아니라, 이 절은 전체 역 기사 공통 상세 배치를 검증한다.

### #146 성능 실측

같은 앞 절 CDP 조건(390×844, CPU4x/150ms/1.6Mbps, 캐시 끔, 경로별3회)으로 a7bb20f의 기존 화면과 #146 최종 앱 변경 내용을 비교했다. 초기와 스크롤 후 전송을 구분한다.

|경로|LCP 전→후(ms)|CLS 전→후|초기 전송 전→후(B)|스크롤 후 전송 전→후(B)|JS 전→후(B)|
|---|---:|---:|---:|---:|---:|
|사당|4200→4212|0.001571→0.001461|1860567→1864396|2056676→2063831|436590→436592|
|구리|3840→3884|0.001558→0.001591|1564415→1599868|1785841→1821453|436213→436592|

12회 모두 HTTP200, 페이지/콘솔 오류·요청 실패·가로 넘침 없음, 스크롤 긴 작업0. 기록은 [station-article-performance.json](./station-article-performance.json)에 있다. 재현은 기존 `measure-design-performance.mjs`의 측정 경로 배열 두 곳만 `/station/sadang/`, `/article/guri-escalator/`로 바꿔 실행하면 된다. 새 측정 프레임워크는 추가하지 않았다.
